# 4.2 油猴请求拦截与编辑 — 设计规划

> 状态：设计规划中（2026-07-17 起）
> 目标：让用户脚本在 **main world** 拦截并编辑**页面自身**发起的网络请求（URL / 头 / body），可取消 / 重定向 / 改写——对齐 Tampermonkey 的 `GM_webRequest`，并泛化为「编辑」。
> 边界：**非 agent 请求编排**（那是 4.3）。4.2 针对页面原生 `fetch`/`XMLHttpRequest`，由用户脚本驱动。

---

## 一、与 4.3 / 4.4 的边界（务必分清）

| 维度 | 4.2 请求拦截与编辑 | 4.3 Agent 请求编排 | 4.4 Main World RPC Bridge |
|------|-------------------|-------------------|---------------------------|
| 拦截对象 | 页面**自身**发起的请求 | agent 内核**自己**发出的请求 | （无，是通道设施） |
| 运行世界 | MAIN world（页面 JS 上下文） | background isolated world | 任意已安装脚本世界 |
| 决策方 | 用户脚本（油猴功能） | agent 内核（beforeRequest/afterResponse hooks） | — |
| 生命周期 | 请求发起前同步/阻塞改 | 请求全生命周期 hooks | RPC 调用通道 |
| 对齐能力 | `GM_webRequest` | 自研编排 | `invokeTool`/`getPageContent` 等 |

结论：4.2 是「页面请求的可编程改写层」，4.3 是「agent 的 request middleware」。两者机制不同、可共享底层（如都走 background 代理发请求），但**不要合并设计**。

---

## 二、核心难点：拦截必须在 MAIN world

- 现状：本扩展的用户脚本经 `chrome.userScripts` 跑在 **USER_SCRIPT 隔离世界**，页面自身的 `fetch`/`XHR` 调用它**看不见**。
- 必须：把拦截器注入页面 **MAIN world**（与页面共享上下文），才能 wrap `window.fetch` 与 `XMLHttpRequest.prototype.open/send/setRequestHeader`。
- 注入手段（经典 TM 技巧）：USER_SCRIPT 世界内 `document.createElement('script')` 把拦截器代码塞进 MAIN world；拦截器与 USER_SCRIPT 世界经 `postMessage` / 已有的 `UserScriptBridge` Port 来回通信。
- 注：`@inject-into main` 在 TAMPERMONKEY_ALIGN.md 中仍属「明确延后」，故当前一律走「MAIN 拦截 + 跨世界回传决策」模式。

---

## 三、拦截层设计

### 3.1 拦截面（MAIN world）
- `window.fetch` → 返回 Promise，天然可 `await` 决策（异步阻塞友好）。
- `XMLHttpRequest.prototype.open` / `setRequestHeader` / `send` → wrap；`send()` 前若有异步决策，**延迟 send** 直到决策 resolve（用闭包队列缓存 body）。
- 采集 `details`：`{ url, method, headers, body, type, initiator }`。

### 3.2 决策回调（USER_SCRIPT world，可经 4.4 bridge 调内核）
拦截器把 `details` 回传 USER_SCRIPT 世界 → 调用户脚本注册的 handler：
- **声明式规则**（`@webRequest` 映射，对齐 TM）：
  ```
  // @webRequest
  { '.*://*.example.com/api/*': { action: 'edit', headers: { 'X-Token': '...' }, body: (b)=>b } }
  ```
- **编程式回调**（`GM_webRequest.onRequest(details) → decision`）：handler 可同步返回，也可 `await` 后返回（如经 4.4 bridge 问内核「这条请求要不要改」）。

#### 3.2.1 规则注册与生命周期（⚠️ 用户拍板，2026-07-17）
- **规则随脚本注册、随脚本存活**：拦截规则是脚本的一部分，写在脚本内（声明式 `@webRequest` 元数据，或脚本初始化时调 `GM_webRequest.onRequest(...)` 注册回调），**不**进全局 `SettingsManager`、也不走 `GM_setValue`。
- **每次脚本初始化时加载**：用户脚本被注入/启用时，其声明的规则随脚本初始化一并注册到拦截层；脚本卸载/禁用时规则一并失效（与 `@tool` 投影随脚本生灭同一思路）。
- 落点：`ScriptsManager` 解析 `@webRequest` + 脚本运行期注册的回调，统一交给拦截层（MAIN world wrapper 在注入时即绑定该脚本的规则集）。多脚本并存时按「脚本维度」隔离规则，互不串扰。
- `decision` 形状：`{ cancel:true }` | `{ redirectUrl }` | `{ requestHeaders, requestBody }` | `{}`（不动）。

### 3.3 阻塞式（与 4.4 微调同脉）
- 用户要求「阻塞式」：拦截器在决策返回前**不把请求放出去**。
- fetch：直接 `await handler(details)` 再构造最终 Request。
- XHR：在 `send()` 内 `await` 决策，再真正 `nativeSend`。
- 超时兜底：决策超时不改请求（fail-open），避免页面卡死。

## 四、响应编辑（⚠️ 已决议：本期不做）
- **用户拍板（2026-07-17）**：响应编辑功能暂时不需要，**响应侧处理默认交给 AI**（agent 拿到响应内容后再决定如何改写/利用）。4.2 严格只做**请求侧**拦截与编辑。
- 故原 P3 的「响应编辑」整项移除，不排入本期。若未来确有页面响应改写需求，再单独立项。

---

## 五、安全与同意
- 请求拦截是隐私敏感能力 → **默认关闭**，需显式 `@grant GM_webRequest`（或新增 `@webRequest` 指令）才注入拦截器。
- 改写鉴权头 / 敏感 body 这类高危操作 → 可复用会话子系统的 danger 确认闸门（SESSION.CONFIRM_*，经 4.4 通道弹确认）。
- 所有拦截/改写经内核 `Log` 打点（info），便于排查与审计。

## 六、落地阶段（建议）

| 阶段 | 内容 | 落点文件 |
|------|------|----------|
| **P0** | MAIN world fetch/XHR 包装器（经 `@grant GM_webRequest` 注入）；支持 `cancel`/`redirect`/`headers` 同步改写；回传通道接 USER_SCRIPT 世界 | `background/gm-api.js` 新增 wrapper 代码；`bridge/UserScriptBridge.ts` 加一条请求/决策 Port 消息类型 |
| **P1** | 异步/阻塞决策：fetch `await`、XHR `send` 延迟；超时 fail-open | 同上 |
| **P2** | 声明式 `@webRequest` 规则 + `GM_webRequest.onRequest` 回调 API（对齐 TM 语义） | `kernel/services/ScriptsManager.ts` 解析 `@webRequest`；`gm-api.js` 暴露 `GM_webRequest` |
| **P3** | background 代理发请求选项（与 4.3 共用，可选）；侧栏规则管理 UI（查看当前各脚本注册了哪些规则） | `sidepanel` 新页面（只读展示，规则仍在脚本内） |

## 七、已决议（原开放问题，2026-07-17 用户拍板）

| # | 问题 | 决议 |
|---|------|------|
| 1 | handler 是否默认可 `await` 内核（4.4 阻塞调用）？ | **可**：默认支持异步/阻塞决策（P1），handler 可经 4.4 bridge 问内核后再返回 decision。 |
| 2 | XHR 延迟 send 的 fail-open 阈值？ | **fail-open**：决策超时（默认阈值，如 3s）则不改请求直接放行，避免页面卡死。 |
| 3 | 「响应编辑」是否进首版？ | **不做**：响应侧处理默认交给 AI；4.2 只做请求侧（见第四节）。 |
| 4 | 规则存储位置？ | **随脚本**：规则写在脚本内、随脚本初始化加载、随脚本生灭；不进 `SettingsManager`、不走 `GM_setValue`（见 3.2.1）。 |
