# Web Agent Client 代码审计与架构审查报告

- **审计对象**：Web Agent Client（Chrome MV3 扩展，`v0.6.7`）
- **审计日期**：2026-07-09
- **审计范围**：内核分层、跨进程接口/契约、类型安全与代码规范、测试与构建、文档/记忆一致性、安全与健壮性
- **方法**：静态通读核心源码（kernel / bridge / background / sidepanel）+ 运行构建 + 运行测试 + 交叉证据核对
- **健康基线**：`npm run build` ✅ 1.30s 通过；`npm test` ✅ 116/116 通过

---

## 一、总评

整体架构**方向是对的**：微内核（Kernel）+ 阶段引导（Bootloader）+ 事件总线（IPC）+ 请求/响应（RPC）+ 传输边界（IPCTransport/serialize）的分层是清晰、可维护的，跨进程序列化处理（`serialize.ts`）尤其扎实。但经过多轮"UI 内外分离"重构后，出现了几处**典型的"半完成重构"遗留问题**，主要集中在**接口契约层**和**类型纪律**上，这也是你最担心的两块。

> **一句话结论**：框架骨架优秀，但"接口优先 RPC"重构只走了一半，且全仓关闭了 TypeScript 严格模式，导致契约死代码、双轨制 RPC、能力系统空转、服务层零测试等问题叠加。优先级最高的两项是 **①开启 TS 严格模式** 和 **②把 RPC 迁移一次性走完（或回退）**。

| 维度 | 评分 | 主要问题 |
|------|------|----------|
| 架构与分层 | 🟢 良好 | ChatProgram 经 `(kernel as any).chatProgram` 挂接，绕开注册表 |
| 接口/契约设计 | 🔴 高风险 | RPC 双轨制 + KernelAPI 死契约 + 能力系统空转 |
| 类型安全/规范 | 🔴 高风险 | `strict:false` + `any` 泛滥 + 基类命名混乱 |
| 测试/构建 | 🟠 中风险 | 构建健康，但服务层/编排层零测试 |
| 文档/记忆一致性 | 🟠 中风险 | 工作记忆与实现严重脱节 |
| 安全/健壮性 | 🟢 良好 | 边界序列化扎实；expose 默认白名单有隐患 |

## 二、审计发现（按维度）

### 维度 A：架构与分层

**A-1（🟠 中）ChatProgram 绕开 Kernel 注册表挂接**
- 位置：`background/main.ts:135-137`
  ```ts
  const chatProgram = new ChatProgram({ kernel, name: 'main' });
  (kernel as any).chatProgram = chatProgram;
  ```
- 问题：Kernel 已有一套规范的 `getSessionManager()`/`getSettingsManager()` 等访问器（`kernel/Kernel.ts:151-157`），但 ChatProgram 却用 `as any` 动态挂到实例上，既无类型声明，也不在注册表生命周期内。破坏了"一切经注册表"的统一原则，且 `kernel.chatProgram` 在别处被访问时完全无类型保护。
- 建议：在 `Kernel` 上声明 `chatProgram: ChatProgram | null` 字段与 `getChatProgram()` 访问器，由 Bootloader 的 START 阶段统一挂接；或把 ChatProgram 也注册为一个 service。

**A-2（🟡 低）双重引导职责模糊**
- 位置：`background/main.ts:77-152`（Bootloader 的 REGISTER/START 阶段）与 `kernel/Kernel.ts:53-74`（`Kernel.boot()`）
- 问题：Bootloader 编排 INIT→REGISTER→START→READY 四阶段，但真正的服务初始化发生在 `Kernel.boot()` 里，而 `kernel.boot()` 又被塞进 Bootloader 的 START 阶段钩子中调用。两套"启动"系统职责边界不清晰，新人容易误用。
- 建议：明确约定——Bootloader 只负责"大阶段编排与 Shell 注入钩子"，Kernel 负责"服务生命周期"；在 `Kernel.boot()` 内不应再被外部阶段包裹，或反之。补一段架构注释说明两者边界。

**A-3（🟢 良性）Manager 直接发 IPC 事件**
- 位置：`kernel/services/SessionManager.ts:57,69`
- 说明：Manager 直接 `this.ipc?.getOrCreateChannel('chat')?.emit(...)` 广播领域事件，耦合了服务层与 IPC。属务实做法，非阻塞，仅记录。

### 维度 B：接口与契约设计（核心风险区）

**B-1（🔴 高）"接口优先 RPC"迁移只完成一半——双轨制并存**
- 服务端现状（`background/main.ts`）：
  - `settings` → 走新契约：`rpcServer.expose('settings', …)`（`:262`）
  - `session`/`tool`/`storage`/`scripts` → 仍走旧 `RPC.*` 枚举，约 20 处 `rpcServer.register(RPC.SESSION_* / STORAGE_* / SCRIPTS_* / TOOL_*)`（`:172-331`）
- 客户端现状（`sidepanel/`）：
  - 仅 `SettingsPage.svelte:81,133,203,219` 用新 `api.settings.*`
  - `ChatPage / HistoryPage / StoragePage / ScriptsPage` 全部仍用 `rpc.call(RPC.*)`（共 20+ 处）
- 影响：同一套"内核对外访问接口"存在**两套命名与两套调用范式**，新同学无法判断该走哪条路；未来每加一个方法都要在"契约 vs 枚举"间二选一，极易漏改。
- 建议（二选一，必须收口）：
  - **方案甲（推荐）**：把 `session/scripts/storage/tools` 的契约在 `KernelAPI.ts` 补全并全部 `expose(...)`，客户端统一 `api.*` 调用，删除 `RPC.SESSION_* / STORAGE_* / SCRIPTS_* / TOOL_*` 枚举与服务端手动 `register`。
  - **方案乙**：明确放弃契约层，连 `settings` 也回退到 `RPC.*`，删除 `KernelAPI.ts` 与 `expose/createApiClient`。

**B-2（🔴 高）`KernelAPI.ts` 中的三份契约是死代码**
- 位置：`kernel/api/KernelAPI.ts:35-70`
- 证据：`SessionServiceContract` / `ScriptsServiceContract` / `StorageServiceContract` 已声明，但全仓**没有任何 `expose('session' | 'scripts' | 'storage', …)` 调用**（grep 确认）。它们从未被绑定到真实 handler。
- 叠加问题：契约方法签名与真实 handler 返回形状**不一致**。例如契约 `getSession(id): Session | null`，而真实 `RPC.SESSION_GET_CURRENT` 返回 `{ session, messages, reasoningEffort }`（`background/main.ts:172-180`）。即使哪天接上，类型也对不上。
- 建议：随 B-1 方案甲一并补全并接线；或随方案乙一并删除。不要让"单一真相源"名存实亡。

**B-3（🟠 中）`RPC.SETTINGS_GET` / `RPC.SETTINGS_SAVE` 已成孤儿常量**
- 位置：`bridge/RPC.ts:44-45`
- 证据：settings 已改用 `settings.getSettings` / `settings.saveSettings`（expose 注册），客户端改用 `api.settings.*`；因此旧枚举 `settings.get` / `settings.save` 既**无服务端注册**也**无客户端调用**，仅在 `RPC.ts` 注释与 `RPC.test.ts`（自注册自测）中出现。
- 建议：删除这两个孤儿常量（及对应注释示例），避免误用后静默失败（"No RPC handler" 错误响应）。

**B-4（🟠 中）三类"线上命名体系"过度分裂**
- `KernelEvents`（`kernel/Events.ts`）：领域事件，如 `chat:messageAdded`
- `CMD`（`kernel/programs/ChatProgram.ts:24-28`）：命令，如 `chat:cmd:send`
- `RPC`（`bridge/RPC.ts`）：请求方法，如 `session.list`
- 问题：三种用途（事件 / 命令 / 请求）各自一套常量，且 `CMD` 与 `KernelEvents.CHAT.USER_APPLY_*` 在 `background/main.ts:159-167` 还做了一次"用户意图 → 内核命令"的转义层。概念上合理，但命名空间缺乏统一前缀约定（有的 `chat:`、有的 `session.`、有的 `chat:cmd:`），检索与排错成本高。
- 建议：在 `Events.ts` 顶部用一段注释明确三套体系的边界与命名约定（已具备雏形，需补强）；`CMD` 可合并进 `KernelEvents.CHAT.CMD_*` 命名空间。

**B-5（🔴 高）`CapabilityManager` 授权链路空转**
- 位置：`bridge/RPC.ts:224-231`（audit 钩子）、`kernel/CapabilityManager.ts`
- 证据：
  1. `expose` 的审计钩子**永远传 `result: true`**（`capHook('invoke', service, [m], true, {})`），不反映真实授权结果；
  2. 全仓**没有任何 `capabilities.declare(...)` 调用**，`_grants` 始终为空；
  3. `CapabilityManager.require()` / `check()` 的拒绝路径**无任何调用方**，是死代码。
- 影响：`CapabilityManager` 目前只是个"永远记录 granted 的日志收集器"，既不做鉴权，也不挡任何调用。它横跨 `Kernel` 构造、`expose` 钩子、构建产物，却零实际作用——典型的"半成品能力"。
- 建议：要么**真正落地**（声明各 service/tool 的 capability，在 `expose`/`invoke` 处调用 `require` 做鉴权，audit 传递真实 result），要么**直接删除**整条链路（Kernel 字段、expose 的 capabilities 选项、audit 钩子），别让它占位。

### 维度 C：类型安全与代码规范

**C-1（🔴 高）TypeScript 严格模式被关闭**
- 位置：`tsconfig.json:6-8`
  ```json
  "strict": false,
  "noImplicitAny": false,
  "strictNullChecks": false
  ```
- 影响：这是全仓质量短板的根源。`any` / `as any` / `(e as Error)` 泛滥由此合法化，空值与未定义错误在运行时才暴露。对于你追求的"规范、高质量"，这是第一优先整改项。
- 建议：分两步走——① 先开 `strictNullChecks: true`（收益最大、破坏性相对可控）；② 再逐步开 `strict: true`。每开一项就修一批 `any`，用 `tsc --noEmit` 量化待修数量。注意：`vite` 构建不依赖 tsc，所以需把 `tsc --noEmit` 加入 CI/预提交，否则严格模式形同虚设。

**C-2（🟠 中）`any` / 强制转换密度过高（抽检）**
- `kernel/programs/ChatProgram.ts:152` `model as any`；`:226,245` `(msg: any) => …`
- `kernel/ToolsManager.ts:193` `_validateArgs(args, schema: any)`
- `kernel/services/SessionManager.ts:154,155` `(value as any)`
- `background/main.ts:172-331` 各 handler `(data: any)`
- 建议：C-1 开启严格模式后，这些会集中暴露，按文件批量收敛为精确类型或 `unknown` + 类型守卫。

**C-3（🔴 高）"接口"层实为命名混乱的抽象基类**
- 位置：`kernel/services/IStorageManager.ts:1`、`kernel/services/ISessionManager.ts:4`
- 证据：
  - `IStorageManager` 是个 **class**，每个方法 `throw new Error('Not implemented')` —— 名为接口，实为会抛错的基类；
  - 文件 `ISessionManager.ts` 里导出的是 `BaseSessionManager`（**文件名 I\* 与类名 Base\* 不一致**）；
  - 同类还有 `BaseSettings` / `BaseScriptsManager` / `BaseProviderAPIService`。
- 影响：I-prefix 通常表示 TS `interface`，但这里它是 class，继承语义（`extends` vs `implements`）易被误用；文件名与类名错位增加认知负担。作者自己的待办（记忆中"统一 I* 的 Base* stub 为纯 interface"）尚未落实。
- 建议：把 `IStorageManager` 等改为真正的 `interface`（用 `interface IStorageManager { … }`），`BaseSessionManager` 等保留为可选的抽象基类但**重命名为 `AbstractSessionManager`** 并让文件名与类名一致。

**C-4（🟠 中）import 路径风格不一致**
- 位置：`kernel/programs/chat/ToolExecutor.ts:16-19` 用别名 `'kernel/models/Tool.js'`；而 `kernel/programs/ChatProgram.ts:13-20` 用相对 `'../models/Message.js'`。
- 建议：统一为别名（`kernel/*`）或统一相对路径，二选一并 eslint 固化。

**C-5（🟠 中）`package.json` 的 `"type"` 与模块形态矛盾**
- 位置：`package.json:21` `"type": "commonjs"`，但代码全用 ESM `.js` 扩展导入（`import './IPC.js'`），且 `manifest.json:28` 声明后台 `"type": "module"`。
- 影响：构建靠 Vite 兜住，但 `"type": "commonjs"` 与新模块写法语义冲突，Node 侧工具（如某些脚本）可能误判。
- 建议：改为 `"type": "module"`（与 manifest 及 ESM 写法一致），或移除该字段让 Vite 全权处理，并校验 `node_modules` 之外的 Node 脚本不受影响。

**C-6（🟠 中）`ToolsManager.getInvocationHistory` 过滤逻辑疑似失效**
- 位置：`kernel/ToolsManager.ts:262-273`
  ```ts
  if (filters.toolName) r = r.filter(e => {
    const callId = e.toolCallId || '';
    return callId.includes(filters.toolName!);   // 用 callId 子串匹配 toolName
  });
  ```
- 问题：`toolCallId` 是生成值（`msg_…` 或 LLM 返回 id），几乎不可能包含 `toolName`，该过滤器实际**永远返回空/错误结果**；且 `:270` `(e as any).timestamp` 读取 `ToolResult` 上可能不存在的字段（`ToolResult` 无 `timestamp`）。属死逻辑 + 潜在 bug。
- 建议：`ToolResult` 增加 `toolName`/`timestamp` 字段，`getInvocationHistory` 改为按 `toolName` 精确匹配；移除 `(e as any)`。

**C-7（🟡 低）持久化层过度吞错**
- 位置：`kernel/services/SessionManager.ts:178-200`（`_persistSessions` / `_persistCurrentSessionId` / `initialize` 全 try/catch + 仅 `Log.warn`）
- 影响：存储配额超限等真实故障会被静默吞掉，排查困难。
- 建议：区分"可忽略"（如首次无数据）与"需上报"（存储写入失败），后者至少 `Log.error` 并考虑向上抛出或由 UI 提示。

### 维度 F：安全与健壮性

**F-1（🟢 良性）跨进程边界序列化扎实**
- 位置：`bridge/serialize.ts`
- 说明：`sanitizeForClone` 处理循环引用（WeakSet）、Date/Map/Set/Error/RegExp、`toJSON` 优先级，且**永不抛异常**——是本项目最稳健的模块之一，正面典型。
- 建议：保持其唯一入口地位（已是 IPCTransport 唯一序列化入口），勿在别处另起炉灶。

**F-2（🟠 中）`RPCServer.expose` 默认"暴露全部公共方法"是危险默认**
- 位置：`bridge/RPC.ts:102-120`（`RPC_EXPOSE_DENY` 用**拒绝列表**自动收集方法）
- 问题：若 `expose` 被调用时省略 `methods`，它会把所有公共方法（减去一份手维护的 deny 名单）自动注册为远程可调用。deny 名单要靠人维护，一旦某 manager 新增敏感方法（如 `resetAll`、`destroy`）而漏进 deny 名单，就被远程暴露。
- 现状：`settings` 用了显式 `methods` 白名单（✅ 安全），所以目前风险被 containment；但**默认行为不安全**。
- 建议：把默认改为 **fail-closed（必须显式传 methods 白名单，否则报错或仅暴露空）**，把 deny 名单机制降级为兜底而非主路径。

**F-3（🟢 良性）Shell 启动竞态处理稳健**
- 位置：`sidepanel/main.ts:45-73`（bootComplete / ping / 3s 超时三路兜底）
- 说明：处理了 SW 被回收、事件错过的竞态，注释清晰。正面典型。

## 四、结论

你的直觉是对的——**经过多轮 UI/内外分离重构，接口层和类型纪律确实出现了"半完成"的裂痕**。但好消息是：骨架（微内核 + 事件/请求双层 + 扎实的边界序列化）是健康的，116 测试 + 1.3s 构建说明工程基础不差。问题集中在"重构没走完"和"类型纪律没收紧"两处，且都**边界清晰、可逐项收口**，不需要推倒重来。

最值得立刻动手的两件事：**① 打开 TypeScript 严格模式**（这是任何"高质量"的前提），**② 把 RPC 迁移一次性收口**（要么全用 `api.*` 契约，要么全回退删掉 `KernelAPI.ts` 与 `expose`）。做完这两点，再补上服务层测试，这个项目就会从"架构优秀但欠打磨"跨入"真正高质量"。
